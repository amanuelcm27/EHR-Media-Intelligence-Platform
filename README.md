# EHR Media Intelligence Platform

A full-stack clinical media search demo: ingest messy EHR exports, clean and audit them, normalize to **FHIR R4**, generate cached **AI clinical summaries**, index everything for **semantic search**, and explore it in an accessible **Tailwind CSS** clinician UI.

> **Synthetic data only.** Every patient, note, lab and report in this repository is generated by `scripts/generate_demo_data.py`. No real PHI is included, and AI output is decision support — not a diagnosis.

---

## Quick start

### Prerequisites

- Python **3.11+** (developed on 3.12)
- Node.js **18+** only if you want to rebuild the Tailwind stylesheet
- Optional: ~90 MB disk for the `all-MiniLM-L6-v2` sentence-transformer model

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"

# Optional: real sentence-transformer embeddings + FAISS
pip install -r requirements-ml.txt

# Build ingestion -> FHIR -> summaries -> vector index (~1 min cold)
python -m ehr_media.cli build

# Serve API + UI
python -m ehr_media.cli serve
```

Open **<http://127.0.0.1:8000>**. API docs: <http://127.0.0.1:8000/docs>.

### macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
pip install -r requirements-ml.txt   # optional
python -m ehr_media.cli build
python -m ehr_media.cli serve
```

### Rebuild the stylesheet (optional)

`frontend/app.css` is committed, so the UI works immediately. To change Tailwind classes:

```bash
cd frontend
npm ci
npm run build      # or: npm run watch
```

### Offline / no-download mode

The platform is offline-first. If `sentence-transformers` or `faiss` is unavailable, it automatically falls back to a deterministic signed-hashing embedder and a NumPy vector index. If no LLM key is configured, summaries use the deterministic offline provider.

```powershell
$env:EHR_EMBEDDING_PROVIDER="hashing"
$env:EHR_LLM_PROVIDER="offline"
python -m ehr_media.cli build
```

## Task coverage

### Task 1 — Ingestion, cleaning and audit

- Loads **JSON**, **CSV** and **plain-text clinical notes**, with source/row provenance.
- Handles missing fields, mixed date formats (`YYYY-MM-DD`, `MM/DD/YYYY`, ISO datetimes, fuzzy text dates), gender variants, and MRN formatting.
- Deduplicates labs and documents, flags possible duplicate patients, and surfaces **conflicting identifiers** (birth date, family name) instead of silently choosing.
- Every record gets an audit entry and data-quality flags (`conflicting_birth_date`, `critical_lab`, `invalid_lab_date`, etc.).
- Demo result: **97 raw records → 51 patients, 69 documents, 175 labs, 51 encounters**, 1 rejected row, 2 identifier conflicts, 221 audit entries.
- Tests cover ambiguous/missing dates, invalid values, duplicates, conflicting identifiers and malformed rows.

### Task 2 — FHIR R4 normalization and validation

- Maps each patient to a **transaction-style Bundle** containing `Patient`, `Encounter`, `DocumentReference`, `Observation` and `DiagnosticReport`.
- Uses `fhir.resources` R4B models for typed parsing **plus** the official HL7 FHIR R4 JSON Schema (`jsonschema`) for strict enum/pattern validation.
- Adds referential-integrity and clinical business rules: every `subject`/`encounter` reference resolves inside the bundle, statuses and required fields are present, attachments carry base64 data and byte sizes.
- Validation results are persisted and exported to `artifacts/reports/fhir_validation_report.{json,md}`.
- Demo result: **51/51 bundles valid, 0 errors, 0 warnings**; 400 total resources.

### Task 3 — AI clinical summaries

- Produces summaries covering **chief concern, diagnoses, recent media, flagged anomalies**.
- Hard limit of **200 words**, enforced after generation, with `confidence`, `confidence_label`, `disclaimer`, provider/model and word count.
- Cache key is **patient ID + SHA-256 record hash**, so unchanged records never re-call the LLM; the cache is persisted in SQLite.
- Providers: Anthropic, OpenAI, or a deterministic offline evidence-based summarizer. `auto` uses a configured key, otherwise offline.
- Demo result: 51 summaries, 100% cached after the first build.

### Task 4 — Semantic search

- Chunks notes, labs, reports, encounters, patient demographics and AI summaries (**454 chunks**).
- Embedding providers: `sentence-transformers/all-MiniLM-L6-v2`, signed feature hashing, or OpenAI embeddings.
- Vector backends: **FAISS** when installed, otherwise **NumPy** cosine search. Both are persisted under `artifacts/index/`.
- `POST /search` returns the top 5 with scores, snippets, AI snippet, confidence and patient/MRN context.
- Filters: resource type, `start_date`, `end_date`, `patient_id`, `min_score`; invalid filters return 422.
- Hybrid score adds a small lexical-relevance boost to cosine similarity for exact clinical terms.
- Warm query latency is **~12–40 ms server-side**; the test suite asserts **50 records in under 2 seconds**.

### Task 5 — Clinician UI

- Tailwind CSS interface with live (250 ms debounced) semantic search and URL state.
- Result cards show patient name, MRN, date, type badge, match score, source snippet and AI summary snippet with confidence.
- Patient detail drawer with **AI summary**, **Documents** and **FHIR resources** tabs, validation banner, data-quality flags and expandable JSON.
- Resource-type chips and date-range filters; skeleton loading, empty, error/retry and offline-index states.
- Responsive one-column → three-column layout; skip link, landmarks, live regions, focus-visible rings, focus trap, Escape-to-close, arrow-key result navigation, `/` search shortcut, and roving-tabindex ARIA tabs.

| --- | --- | --- |
| `GET` | `/health` | Build status, counts and index metadata |
| `GET` | `/filters` | Available resource types and date range |
| `POST` | `/search` | Semantic search with filters |

| `GET` | `/fhir/{resource_id}` | One stored FHIR resource |

### Search example

```bash
curl -X POST http://127.0.0.1:8000/search \
  -H "content-type: application/json" \
  -d '{
    "query": "heart failure with shortness of breath",
    "top_k": 5,
    "resource_types": ["DocumentReference", "DiagnosticReport"],
    "start_date": "2025-01-01",
    "end_date": "2026-12-31"
  }'
```

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/search `
  -ContentType "application/json" `
  -Body '{"query":"critical potassium","top_k":5}'
```

### CLI examples

```powershell
python -m ehr_media.cli search "sepsis antibiotics lactate" --top-k 5
python -m ehr_media.cli patients --limit 10
python -m ehr_media.cli summarize pat-4f20790390c154f1
python -m ehr_media.cli stats
```

Copy `.env.example` to `.env` or set environment variables:

| `EHR_LLM_PROVIDER` | `auto` | `auto`, `anthropic`, `openai`, `offline` |
| `EHR_ANTHROPIC_API_KEY` / `EHR_OPENAI_API_KEY` | empty | Optional |
| `EHR_MAX_SUMMARY_WORDS` | `200` | Hard summary cap |
| `EHR_DEFAULT_TOP_K` | `5` | Default result count |

API keys are optional. The demo runs fully offline with deterministic fallbacks.

## Design decisions

1. **Offline-first with graceful degradation.** Optional ML/LLM dependencies never block the demo; hashing embeddings and a rule-based summarizer keep the full flow runnable with only core dependencies.
2. **Two-layer FHIR validation.** `fhir.resources` catches model/type errors, while the official HL7 R4 JSON Schema catches enum/pattern issues the models may accept. Business-rule checks add reference integrity.
3. **Plain-dict FHIR resources.** Resources are validated then stored as JSON, which keeps the store simple and makes the API/FHIR JSON exactly what clinicians and downstream systems see.
4. **SQLite as the system of record.** One file holds patients, resources, bundles, validation, summaries, chunks and audit entries — easy to run, inspect and reset for a demo.
5. **Hash-based summary cache.** Keying on patient ID plus a SHA-256 of the normalized record makes cache invalidation deterministic and avoids stale clinical summaries.
6. **Hybrid retrieval.** Cosine similarity handles paraphrase; a small lexical boost keeps exact drug/lab/diagnosis names competitive.
7. **Accessibility as a feature.** Semantic landmarks, live regions, visible focus, a focus trap, keyboard grid navigation and ARIA tabs are implemented directly rather than bolted on.

## Tradeoffs and limitations

- **Synthetic scale.** 51 patients / 454 chunks is enough to demonstrate the design, not to prove production retrieval quality.
- **SQLite + in-process FAISS.** Great for a single-node demo; concurrent writers, horizontal scaling and incremental index updates would need Postgres/pgvector or a managed vector store.
- **No authentication/RBAC.** A real EHR deployment needs SSO, least-privilege scopes, immutable audit storage and encryption/key management.
- **Offline summaries are extractive.** They are deterministic and safe, but less fluent than a hosted LLM. LLM output is not clinically validated.
- **Date granularity.** Most resources are date-only; partial dates and timezone edge cases are normalized conservatively and flagged.
- **Binary media.** Document attachments are represented as base64 inside FHIR `Attachment` for portability, not as a production object store.
- **Not a FHIR server.** Bundles are validated and stored, but there is no full FHIR REST facade, search-parameter engine or terminology service.

## Possible improvements

- Add OIDC/SSO, role-based access and per-patient consent checks.
- Replace SQLite with Postgres + pgvector and add incremental embedding updates.
- Add a de-identification pipeline and PHI redaction before any external LLM call.
- Add retrieval/answer evaluation (Recall@k, MRR, clinician relevance review) and summary faithfulness checks.
- Stream LLM summaries, add human approval/editing, and store prompt/model versions with each summary.
- Expose a FHIR REST facade (`Patient`, `DocumentReference`, `DiagnosticReport` search) and SMART-on-FHIR launch.
- Add end-to-end browser tests (Playwright) and visual regression checks.
